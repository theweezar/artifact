How Viecoi's Cache Framework Works Today

Job-search and site-layout responses are cached through one shared system, CacheManager, instead of each feature rolling its own caching logic. This page explains what gets cached, for how long, how it refreshes itself automatically, and how staff can clear it — in plain English, backed by what was actually found reading the code on 2026-10-24.

The strategy in one paragraph

Most job-search pages are computed once and then served from Redis for a fixed window (a TTL). Rather than letting a cached page suddenly expire and forcing one unlucky visitor to wait for a slow recompute, the busiest entries use stale-while-revalidate (SWR): once the TTL passes, the old answer keeps being served instantly while a fresh one is quietly recomputed behind the scenes. On top of that, a nightly job proactively warms a curated list of popular URLs at 4am, before the next day's traffic arrives, so visitors are less likely to ever hit a slow first-computation. Staff can also force a cache entry or an entire category to be cleared on demand through an internal clear endpoint.

Request Lifecycle — Compute, Cache, Serve, Refresh, Expire

Every cache read goes through CacheManager::remember() (or rememberMany() for batch id lookups — see note below). It stores each cached value as two Redis keys: the data itself, and a short-lived "fresh" marker. Whether the marker is still alive is what decides if a request gets a fast fresh hit, a fast-but-stale hit, or a cold compute.

flowchart TD
    A["Request for a cached entry\n(e.g. job-search.results)"] --> B{"fresh marker\npresent?"}
    B -- "yes" --> C["✅ FRESH HIT\nreturn cached value immediately"]
    B -- "no" --> D{"data key\nstill present?"}
    D -- "yes (expired fresh marker,\nhard TTL not yet reached)" --> E["🟡 STALE HIT\nreturn the OLD value immediately"]
    E --> F{"revalidation\nalready running?\n(NX lock, max 300s)"}
    F -- "no" --> G["dispatch RevalidateCacheJob\n(queue, or inline if QUEUE_CONNECTION=sync)"]
    G --> H["recompute via the entry's\nComputeResolver"]
    H --> I["write data key + reset\nfresh marker"]
    F -- "yes" --> J["skip — another\nrequest is already\nrevalidating"]
    D -- "no (hard TTL expired\nor never cached)" --> K["🔴 MISS\nacquire lock, compute\nSYNCHRONOUSLY"]
    K --> L["caller waits for the\ncompute to finish"]
    L --> I
    C --> M(("response"))
    E --> M
    L --> M
Fresh hit — instant, no compute Stale hit — instant, refresh happens in background Miss — visitor waits for a synchronous compute
✓

Verified Mechanism confirmed by reading App\Services\Cache\CacheManager directly: the hard-TTL data key is kept alive for ttl + swr_stale_ttl, while a separate {key}:fresh marker expires after ttl alone. A {key}:revalidating NX lock (max 300s) prevents duplicate background recomputes when many requests hit a stale entry at once. If Redis itself is unreachable, the manager fails open — it computes the value uncached rather than erroring, unless the compute step itself throws.

⚠

Caveat job-search.result-ids and job-search.hydrator-item (per-id batch lookups used by hydrators) are read via rememberMany(), a separate MGET/pipeline path that does not go through resolveKey() or SWR at all — they are plain fixed-TTL cache-aside, with no stale-while-revalidate and no warm-cache support.

Warm-Cache Computation Schedule

A console command, cache:precompute-urls, proactively recomputes a curated list of popular job-search URLs so the first visitor of the day doesn't hit a cold cache. This is separate from, and happens before, normal traffic-driven SWR refreshes.

    T["⏰ Scheduled trigger\n04:00 Asia/Ho_Chi_Minh\n(Laravel scheduler)"] --> G{"schedule_enabled?\n(VIECOI_API_CACHE_PRECOMPUTE_SCHEDULE_ENABLED)"}
    G -- "no" --> X["skipped, no-op"]
    G -- "yes" --> R["read storage/app/cache-warm-urls.txt\n(or --file= override)"]
    R --> U["for each URL:\nresolve via PublicJobSearchUrlResolver\n→ build context + criteria"]
    U --> S{"for each scope in\nVIECOI_API_CACHE_SCOPES_ALLOWED_PRECOMPUTE\nthat has a ComputeResolver"}
    S --> D["delete existing cache key(s)\n(+ :fresh / :revalidating for SWR entries)"]
    D --> C["call the scope's ComputeResolver\ndirectly, then CacheManager::remember()"]
    C --> L["log per-URL result;\nfinal JSON summary\n{status, urls, refreshed, skipped, failed}"]
    L --> LOG[("precompute_cache_urls\nlog channel — daily file,\n14-day retention")]

Invalidation / Manual Clear

Besides automatic TTL expiry and SWR refresh, staff can force a cache entry (or a whole category) to be dropped via one internal endpoint: POST /api/v3/internal/cache-tools/clear, guarded by a shared secret header.

flowchart TD
    A["POST /internal/cache-tools/clear\n(scope, url?) + secret header"] --> S{"secret header\nvalid?"}
    S -- "no" --> R1["401 — request refused"]
    S -- "yes" --> B{"url provided?"}
    B -- "yes, exact URL" --> C["delegate to the scope's\nCacheClearService\n(e.g. JobSearchCacheClearService)\n→ clears that one cache key"]
    B -- "no → clear ALL\nfor this scope" --> D["loop every cache_policy entry\nin this scope"]
    D --> E{"entry's\nallow_clear_cache\n= true?"}
    E -- "no" --> F["skip this entry entirely"]
    E -- "yes" --> G["SCAN for matching keys via\nRedisUtil::collectByPattern(prefix + '*')"]
    G --> H["delete each matched key\nONE AT A TIME\n(not a single bulk DEL)"]
✓

Verified "Clear all" is not a blind scope-wide wipe — each entry is checked individually against allow_clear_cache first, which is why layout.navigation and layout.footer (sharing one public-layout scope) can be cleared independently without wiping each other. Matched keys are deleted one at a time rather than in one bulk DEL call — this split exists specifically to avoid a suspected bug where a multi-key delete could straddle Redis Cluster hash slots and silently fail on some keys.

Cache Key Shape

Every key written by CacheManager follows one fixed template so different environments, scopes, and endpoints can never collide:

{ENV}__{SCOPE}__{ENDPOINT_KEY}[__{business_date}]__{resolved_key}[{version}]

{ENV}App environment (local/staging/production) — keeps environments from colliding if they ever share one Redis instance
{SCOPE} / {ENDPOINT_KEY}Upper-cased scope and the raw endpoint key, each sanitized (non-alphanumeric runs collapsed to _) so a dash or dot in a name can't be mistaken for the __ separator
{business_date}Only appended if an entry sets use_date_prefix: true. Verified — no entry currently does this.
{version}Appended when the entry has a version strategy (e.g. job-search.seo/.results/.result-ids/.hydrator-item use a sync-watermark version)
⚠

Caveat, verified in code If an entry ever turns on use_date_prefix, the SCAN prefix used for "clear all" bakes in today's date — a clear would then only reach today's dated keys, not older days left over from TTL. Not an active bug today since no entry uses date prefixing, but worth knowing before enabling it.

Layout Caching (public-layout scope)

Site-wide layout pieces are split by how dynamic they are:

PieceCached?Notes
Navigation, Footer✓ cached, ~7 daysReal CacheManager entries under shared public-layout scope; each has a verification strategy that detects and recomputes on a known truncated-payload bug — a guard, not a fix. Root cause still unknown
Session, Shell, Locales✗ never cachedPer-session/per-request data; resolved directly, uncached, on every request, by design

A related detail: the site's menu/category data has its own separate, long-lived (6-month) cache inside MenuCategoryService. When the navigation flow builds its response, it deliberately skips that inner menu cache (handleMenuV2($hostId, useCache: false)) because the outer layout.navigation entry already wraps the whole response — avoiding caching the same data twice at two different layers. Other callers of the menu service still use its cache normally.

Cache Tools UI (Admin Frontend)

An internal admin page in viecoi_nextjs lets staff trigger the clear endpoint above without needing API access directly.

  • Per-URL scopes (job-search, job-search-hot-company) show a URL input and a "Clear" / "Clear all" choice.
  • Global scopes (currently just public-layout) show a language + host picker instead, with a single "Clear" button — there's only one way to clear a global scope today.
⚠

UI placeholder, verified in code The language/host picker shown for global scopes is not wired to anything yet — whatever is selected is never sent to the backend. Clicking "Clear" always clears the entire public-layout scope regardless of the selection. This is an intentional placeholder for a possible future per-language/per-host clear, explicitly deferred.
