Viecoi API 分割
アーキテクチャノート · チームレビュー用

Viecoiをビジネス領域ごとに2つのリポジトリへ分割する

V3の実装を develop から master へコミット単位で移植し続けるのをやめ、2つのブランチをそれぞれ独立したリポジトリにする。分割の境界は、すでに実態として存在している責務の違いに沿わせる。viecoi-api ではなく viecoi-v3-api と名付けたのは意図的な選択 — 将来V4の刷新が必要になった際、ゼロから作るのではなくこのリポジトリからフォークできるようにするため。

リポジトリ: viecoi · viecoi-v3-api 共有基盤: MySQLデータベース1つ 状態: 承認済み — 実行開始

領域の分け方

各リポジトリはプロダクトの明確に異なる部分を担う。これは将来の理想像ではなく、2つのブランチが今すでにそう振る舞っている実態そのもの。

Source of Truth

viecoi

  • すべてのデータベースマイグレーション — スキーマの唯一の管理元
  • Cronジョブ
  • Employer向け機能のV2 API
  • Employer向けReact webappページ
  • 既存の確立されたサービス層を引き続き使用
新しい領域

viecoi-v3-api

  • V3 APIのみ
  • GuestとJobseeker向けページのレンダリングに限定
  • サービスはすべて新規実装 — viecoiの既存サービス層は再利用しない
  • やむを得ない例外: Auth、session、layout-shellのbootstrap部分は共有を継続
同じ物理データベースに対して読み書きする — 別スキーマなし、read replicaなし

コードが裏付けている事実

2つのブランチを実際に比較し、18個のV3コントローラーが実際にimportしている全サービスクラスを追跡した結果 — 推測ではない。

74% V3がimportする65個のサービスクラスのうち、developにしか存在しない — 本当に新規で、再利用ではない
26% 意図的に共有されている — Auth、session、layout-shellのbootstrapは両側に存在
55% V3のサービスはEloquentを一切使わず、生SQLのDB::table()で物理テーブルに直接クエリしている
13 実際に共有されているEloquentモデル — 変更頻度の低い小さな参照・識別用テーブルのみ

残るリスク: サービスではなくスキーマ

「サービスを再利用しない」という原則はコード上で確かに守られている。しかしそれは結合を取り除いているわけではなく、一段下の層 — データベース自体 — に移しているだけ。viecoi-v3-apiはviecoiと同じ物理テーブルを読み、その半分以上がEloquentではなく生SQLで行われているため、viecoiのマイグレーションでのカラムのリネームや削除は、コンパイルエラーもなく、共有クラスもなく、どちらのリポジトリにもテストもないままviecoi-v3-apiのページを壊しうる。

共有されている13個のモデルは小さく制御可能なリスクにすぎない。テーブル名・カラム名への生SQLの依存こそが本当のリスクであり、2つのうちで最も見えにくい破損モードだ。

なぜ「ガードレール」が必要で、プロセスルールだけでは足りないのか

どちらも、リリース前に誰かが影響に気づく可能性を上げる。しかし片方だけが「誰かが覚えていること」の限界を超えてスケールする。だからTask 2は、プロセスルール単独ではなくガードレールを中心に据える。

手動レビュー

プロセス

viecoiのマイグレーションチケットを実装する担当者が、マージ前にviecoi-v3-apiへの影響を確認する責任を持つ。

記憶に依存し、さらに担当者がそもそも別リポジトリを開こうと思うかどうかにも依存する。

AIガードレール

CLAUDE.md / AGENTS.md

リポジトリの指示で、AIコーディングアシスタントがviecoiのマイグレーションに触れるたびにviecoi-v3-apiの生SQL依存を確認するようにする。

アシスタント経由の変更にしか発火しない — 使わない人には何も知らせない。

Task 2がまだ閉じる必要があるゲート

ガードレールと新しいテストスイートが本当に機能するのは、マイグレーションがマージされる前に、viecoiの変更予定のスキーマに対してそのテストが実際に実行された場合のみ — マージ後では意味がない。モックされたテストではこれは実現できない。スキーマがどれだけずれても常にグリーンのままだからだ。テストは実際にマイグレーション済みの本物のデータベースに対して実行される必要があり、そのスキーマに対してviecoi-v3-apiのテストスイートを必須チェックとして走らせるのはviecoi自身のパイプラインでなければならない — そうでなければこれは事後の検知にすぎず、事前の防止にはならない。

実行計画

2つの作業ストリーム、着手可能。

Task 1

正式なソースを、正しい範囲で立ち上げる

リネーム
developを独立したリポジトリへ切り替える: viecoi-v3-api。
整理
新しいリポジトリを走査し、V3 APIの範囲外にあるものをすべて削除する — コントローラー、コンソールコマンド、その他viecoi-v3-apiが実際に所有していないものすべて。
環境構築
両方の環境でgitとnginxを設定する。
wct-1 — 本番環境 wct-2 — ステージング環境
ドメイン
環境ごとにV3 APIバックエンドのドメインを設定する。
api.viecoi.vn — 本番 stgapi.viecoi.vn — ステージング
DNS
Cloudflare側で両ドメインのDNSを正しいサーバーIPへ向ける — api.viecoi.vn → wct-1、stgapi.viecoi.vn → wct-2。
Task 2

スキーマリスクに対するガードレールとルール

統合
V3が所有するマイグレーションとseederをすべてviecoi-v3-apiからviecoiへ移すことで、スキーマの所有権に例外をなくす — viecoi-v3-apiには自前のマイグレーションが1つも残らない状態にする。

具体的には: 8個のマイグレーション（例: add_company_search_filter_indexes、add_term_for_seo_to_tag_technique）と4個のseeder（3個のseederクラス + database/seeders/data/VIO3788/配下のCSVフィクスチャ1個）が現在developにしか存在しない — これらが実際に移すべき対象。

起草
viecoi用のCLAUDE.md / AGENTS.md — スキーマの変更には必ずviecoi-v3-api側の対応するテスト更新を伴わせる。厳格な遵守が必須
構築
18個のV3コントローラーすべてをカバーする最初のテストスイートを書く — 上のガードレールが初日から実効性を持つように。

実際にマイグレーション済みのデータベースに対する、レスポンス内容への具体的なアサーションを含むfeatureレベルのテストである必要がある — モックされたunit testではスキーマのずれに関わらずグリーンのままになってしまう。ブランチカバレッジが最も重要なのは、生SQLのリスクが集中しているsearch/detail系のコントローラー。
