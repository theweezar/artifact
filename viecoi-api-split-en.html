Viecoi API Split
Architecture note · for team review

Splitting Viecoi into two repositories by business scope

Instead of continuing to port V3 work commit-by-commit from develop into master, we stop merging and let the two branches become two repositories, divided along the responsibilities they already have in practice. Named viecoi-v3-api rather than viecoi-api on purpose — if a future V4 rewrite is ever needed, it forks from this repo instead of starting over.

Repos: viecoi · viecoi-v3-api Shared substrate: one MySQL database Status: approved — execution starting

The scope split

Each repo owns a distinct slice of product surface. Nothing here is aspirational — it's how the two branches already behave today.

Source of truth

viecoi

  • All database migrations — the single schema authority
  • Cron jobs
  • V2 APIs for Employer features
  • Employer-facing React webapp pages
  • Continues to use the existing, established service layer
New surface

viecoi-v3-api

  • V3 APIs only
  • Renders Guest and Jobseeker-facing pages exclusively
  • Services are written fresh — no reuse of viecoi's existing service layer
  • Exception, by necessity: Auth, session and layout-shell bootstrapping stay shared
reads and writes against the same physical database — no separate schema, no read replica

What the code confirms

Measured directly against the two branches, tracing every service class the 18 V3 controllers actually import — not an estimate.

74% of V3's 65 imported service classes exist only on develop — genuinely new, not reused
26% are shared on purpose — Auth, session, and layout-shell bootstrapping present on both sides
55% of V3 services skip Eloquent entirely and query physical tables with raw DB::table() SQL
13 Eloquent models actually shared — small, low-churn reference and identity tables

The residual risk: schema, not services

The "no reused services" rule holds up in the code. But it doesn't remove the coupling — it just moves it one layer down, to the database itself. Because viecoi-v3-api reads the same physical tables as viecoi, and over half of it does so through raw SQL rather than Eloquent, a column rename or drop in a viecoi migration can break a viecoi-v3-api page with no compiler error, no shared class, and no test in either repo to catch it.

The 13 shared models are a minor, containable risk. The raw-SQL dependency on table and column names is the real one — it's the least visible failure mode of the two.

Why a guardrail, not just a process rule

Both raise the odds someone notices the impact before it ships, but only one scales past whoever happens to remember. That's why Task 2 leads with the guardrail rather than the process rule alone.

Manual review

process

Whoever implements a viecoi migration ticket is responsible for checking its effect on viecoi-v3-api before merging.

Relies on memory, and on that developer thinking to open a second, separate repository at all.

AI guardrail

CLAUDE.md / AGENTS.md

Repository instructions tell an AI coding assistant to cross-check viecoi-v3-api's raw-SQL dependencies whenever it touches a migration in viecoi.

Only fires when the change is made through the assistant — silent for anyone who isn't.

The gate Task 2 still needs to close

The guardrail plus the new test suite only bites if something actually runs those tests against viecoi's proposed schema before a migration merges — not after. Mocked tests won't do this: they'd stay green regardless of drift. The tests need to hit a real, currently-migrated database, and viecoi's own pipeline needs to be the one triggering viecoi-v3-api's suite against that schema as a required check — otherwise this is detection after the fact, not prevention.

Execution plan

Two work-streams, ready to start.

Task 1

Stand up the official source, correctly scoped

Rename
Switch develop into its own repository: viecoi-v3-api.
Trim
Scan the new repository and remove everything outside the V3 API surface — controllers, console commands, and anything else that isn't part of what viecoi-v3-api actually owns.
Provision
Configure git and nginx on both environments.
wct-1 — main environment wct-2 — staging environment
Domain
Configure the V3 API backend domain per environment.
api.viecoi.vn — main stgapi.viecoi.vn — staging
DNS
Point Cloudflare DNS for both domains at the correct server IPs — api.viecoi.vn → wct-1, stgapi.viecoi.vn → wct-2.
Task 2

Guardrail and rules for schema risk

Consolidate
Move every V3-owned migration and seeder out of viecoi-v3-api and into viecoi, so schema ownership has no exceptions — viecoi-v3-api ends up with zero migrations of its own.

Concretely: 8 migrations (e.g. add_company_search_filter_indexes, add_term_for_seo_to_tag_technique) and 4 seeders (3 seeder classes + 1 CSV fixture under database/seeders/data/VIO3788/) exist only on develop today — these are what actually need moving.

Draft
CLAUDE.md / AGENTS.md for viecoi — any schema change must come with a matching test update in viecoi-v3-api.must comply strictly
Build
Write the initial test suite covering all 18 V3 controllers, so the guardrail above has something to enforce from day one.

Needs to be feature-level tests against a real migrated database with assertions on actual response content — not mocked unit tests, which would stay green regardless of schema drift. Branch coverage matters most on the search/detail controllers, where the raw-SQL surface concentrates.
